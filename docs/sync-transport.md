# 局域网同步的 TLS 基础

## 网络栈选型

下表使用 Maven 构件的压缩体积，未计入 APK 的 DEX 转换与打包开销。

| 方案 | 主要构件体积 | 维护成本 |
| --- | --- | --- |
| Ktor Client + Ktor Server | 3.6.0 的 OkHttp 客户端引擎、客户端核心、CIO 服务端引擎和服务端核心合计约 2.06 MiB，另有传递依赖 | Ktor 提供 HTTP 路由和协程支持。CIO 服务端缺少 TLS 监听，其他服务端引擎需要验证 Android 兼容性。 |
| OkHttp + 自建 HTTPS 服务端 | OkHttp Android 5.3.2 和 Okio JVM 3.16.4 合计约 1.19 MiB，另计服务端 | 需要在两端维护不同的 HTTP API，并选择 Android 可用的服务端。 |
| JSSE TLS socket | Android 和桌面 JVM 自带 TLS。桌面生成 X.509 证书使用 Bouncy Castle PKIX 1.87，三个 JAR 合计约 9.08 MiB。 | 在 `jvmAndAndroidMain` 共享客户端、服务端和证书校验。应用协议的消息边界与版本握手由后续同步实现负责。 |

当前采用 JSSE。最低协议版本为 TLS 1.2，系统提供 TLS 1.3 时也启用。配对后的连接从信任列表读取对端指纹，客户端和服务端都用它校验对端。指纹取证书 DER 编码的 SHA-256 摘要，再编码为无填充 Base64URL。阻塞式套接字运行在 IO 线程。

## 设备证书和私钥

- Android 使用 `AndroidKeyStore` 中不可导出的 P-256 私钥和自签名证书。Ed25519 种子用 Keystore 的 AES-GCM 密钥封装，密文保存在应用的 no-backup 目录。这让支持不同 Keystore 算法的 Android 设备使用同一种配对身份。
- 桌面使用 `~/.keyvault/sync-tls.p12`。调用方提供口令并在使用后清理字符数组。私钥条目以 PBKDF2-HMAC-SHA256 和 AES-256 加密，首次保存时原子提交。错误口令会让加载失败，原设备证书仍保留在文件中。
- P-256 密钥用于 TLS，Ed25519 密钥用于签署配对请求。桌面的两个私钥存于同一个 PKCS#12 文件，用进入配对页面时输入的口令解锁。设备身份、配对码和业务内容无需写入日志。

## 首次配对

Android 从「配置管理」进入「局域网配对」，桌面从侧栏进入「局域网同步」。两台设备需处于同一 IPv4 子网。发起端选择「显示配对二维码」后，Android NSD 或桌面 JmDNS 会在局域网广播临时服务名。发现失败时仍可扫描二维码直连。Android 使用相机，桌面可读取二维码图片或截图，两端都可粘贴配对码。

配对码有效期为两分钟。码内的 Ed25519 签名覆盖发起端身份、TLS 指纹、本机地址、端口、一次性随机数和临时 X25519 公钥。发起端校验接收端的签名以及 TLS 实际使用的证书。两端根据临时共享密钥和双方身份各自计算校验码。请在两台设备上比对完整校验码，再分别确认。整张二维码被替换成另一台设备的有效邀请时，需要靠这一步确认实际对端。

一次邀请只接受一份通过校验的请求。发起端在收到这份请求后关闭临时监听，再等待双方用户确认。两边均确认后，各自在 DataStore 原子保存 Ed25519 公钥和 TLS 指纹。连接在最后确认阶段中断时，可重新扫码配对同一设备。已保存身份的公钥或证书变化会被拒绝。

## 单次配置传送

在两端打开「局域网配对 → 传送配置」。接收端选择已配对的发送设备并点「开始接收」。发送端选择接收设备和一份配置，再扫描或粘贴接收码。接收端保存为新配置，重名会加序号。

连接在固定对端证书的双向 TLS 内完成协议版本握手，随后发送含传送 ID、配置 ID、条目数、总字节数、分块大小与整体 SHA‑256 的 manifest。每块 64 KiB，最后一块可更短。接收端为每次连接生成新的 HMAC‑SHA256 密钥，并通过 TLS 发给发送端。认证标签覆盖 manifest 的 SHA‑256、块序号和数据。接收端校验成功后才确认该块，提交前还会校验完整配置的 SHA‑256、条目数和结构。

接收端在当前会话的内存中保留已确认的分块，配置上限为 4 MiB。断线时两端保留传送页面，发送端会自动重连，也可手动重试。如果接收端退出、重启或重新开始接收，已有分块会被释放，尚未完成的传送从第一块开始。重新扫码可以沿用发送端的同一次传送。完整配置和回执由一次 DataStore 事务提交，确认丢失或接收端重启后，凭同一发送设备及传送 ID 重试只返回已有回执。

## 增量同步

首次可用「发送配置」和「接收配置」建立副本。之后一端选择「等待增量同步」，另一端选择「发起增量同步」。两端各选同一配置的本地副本和已配对的对端，再扫描或粘贴等待端显示的同步码。首次成功同步会绑定这两份副本。一份配置可绑定多台设备，每台设备对应一份副本。

同步比较服务、配置项和 Key 的稳定 ID、版本向量及内容摘要，只发送对端缺少或需要比较的正文。独立编辑会合并。两端同时改同一条目时，普通修改默认采用更新时间较新的版本。并发删除默认采用删除。进入「同步冲突与历史」可选择保留本机或对端版本，下一次同步会传播选择。待处理的两个版本随配置保存在本地 DataStore。

删除记载 `deletedAt`。30 天后在下一次保存或同步时清理删除时间，仍保留条目 ID 和删除版本，以拦截长期离线设备的旧副本。升级时用现存条目建立版本基线，升级前已删除的条目没有可传播的删除记录。

双方在固定证书的双向 TLS 上交换清单。每次连接使用新的 HMAC 密钥，帧认证覆盖方向、严格递增的序号、消息类型和正文。接收端拒绝不连续的序号、无效标签和已结束的同步轮次。传送中的分块在当前同步会话中保留，临时断网后自动重连续传。退出页面或重启要开始新一轮同步。每台设备会将合并结果、冲突和轮次回执一次性写入本地 DataStore。

## 多设备与后台同步

在「局域网配对」的已配对设备列表中点选设备，即可撤销信任。正在进行的连接会关闭，该设备要重新配对才能再连接。已同步的配置仍可在本机编辑。

两端各完成一次手动增量同步后，都可选择「开启后台同步」。启用期间，使用上次确认的 IPv4 地址和 TCP `36541` 定时同步已绑定的副本。每对设备由一端发起，双方在同一轮交换变更。对端不可达时稍后重试。若局域网分配了新地址，通过手动同步更新地址。

- Android 只能从可见的应用界面开启。前台服务窗口最多开启 30 分钟，可通过通知或应用内按钮停止。系统终止进程后，重新打开应用并再次开启窗口即可追上离线期间的变更。
- 桌面在支持系统托盘的环境中，开启同步后关闭窗口会缩到托盘。右键托盘图标可以打开窗口、停止同步或退出。应用退出后，再次打开时需重新解锁并开启同步。
- 「同步冲突与历史」可查看每份配置最近 30 天内最多 100 条已处理记录，也可手动清除。历史只保存条目 ID、处理方式和时间。

## 验证

`./gradlew :shared:jvmTest` 检查桌面私钥条目加密、错误口令、证书指纹持久化和双向 TLS 的成功与拒绝路径。

连接 Android 测试设备后，从仓库根目录执行以下命令。测试通过 `adb reverse` 连接桌面本地 TLS 服务，检查两端协商的版本相同，并在握手后交换测试字节。

```sh
./gradlew :androidApp:assembleDebug :androidApp:assembleDebugAndroidTest
adb install -r androidApp/build/outputs/apk/debug/androidApp-debug.apk
adb install -r -t androidApp/build/outputs/apk/androidTest/debug/androidApp-debug-androidTest.apk
KEYVAULT_TEST_ADB=adb ./gradlew :shared:jvmTest --rerun-tasks
```

PowerShell 中在执行最后一条 Gradle 命令前设置 `$env:KEYVAULT_TEST_ADB = 'adb'`。连接多台设备时用 `ANDROID_SERIAL` 指定目标。

Android 和桌面处于同一 IPv4 子网时，设置 `KEYVAULT_TEST_LAN=1` 可额外测试 Android 广播、桌面直连配对、500 个 Key 的配置传送和进程强制停止后的后台追赶。后台测试会打开调试版应用、启动前台同步服务并按 Home。设置 `KEYVAULT_REQUIRE_MDNS=1` 会要求发现广播。设置 `KEYVAULT_TEST_DESKTOP_HOST=1` 会测试桌面发起、Android 发现并连接。测试使用独立的配对和配置记录文件。
